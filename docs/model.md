# 模擬模型（engine model）

這份文件說明模擬器怎麼算。數字要可信，假設就要寫清楚。

## 1. 時間和事件

- 時間單位是毫秒（ms）。
- 引擎是離散事件模擬（discrete-event simulation）：每件事是一個「在時間 t 要做的事」，放在最小堆積（min-heap）裡，依時間順序執行。同一時間的事件依加入順序執行。
- 同一個設計、同一個情境、同一個種子（seed），結果完全一樣。

## 2. 流量

- 到達：預設是 Poisson（隨機到達，間隔服從指數分佈）。也可以選 `constant`（等間隔）：下一個請求在「流量曲線下的面積」累積到 1 個請求時送出，所以兩個請求之間的短暫突波（cron、spike）也會算到。
- 突波（spike）、爬升（ramp）、週期（wave）和排程（cron）用 thinning 做：把時間在每個事件的開始和結束點切段，每段先用該段的最高速率產生候選到達，再依當下速率接受。
- 週期流量（`wave`）：倍數是 1 + `amplitude` × sin(2π(t − atS) / `periodS`)。`periodS` 是壓縮過的一天，例如 120 秒一輪。整數輪的平均倍數是 1。
- 排程突波（`cron`）：從 `atS` 起每 `everyS` 秒一次，所有使用者在 `burstS` 秒內一起送出，這段時間倍數是 `multiplier`。加上 `jitterS` 時，同樣多的額外請求分散在 `burstS + jitterS` 秒內送出，倍數變成 1 + (`multiplier` − 1) × `burstS` / (`burstS` + `jitterS`)。所以 jitter 不減少請求，只降低尖峰。
- GC 停頓（`pause`）：從 `atS` 起，節點每 `everyS` 秒停 `pauseMs` 毫秒（stop-the-world）。停頓時這台實例不做任何處理：正在做的工作暫停，停頓結束才繼續；新請求照常排隊。每台實例各自 GC：第 i 台的停頓往後移 i ÷ 台數 個週期。負載平衡器不知道哪一台在停頓（真實的負載平衡器也不知道）：least_conn 和 p2c 看到那台的進行中請求變多，就少送給它；round robin 和 random 照樣送，所以送到停頓那台的請求要等停頓結束。只有會處理請求的元件（API 伺服器、API Gateway、worker、快取、資料庫、物件儲存）受影響。
- 流量移轉（`shift`）：從 `atS` 起，把 `from` → `to` 這條線（同樣兩端的每一條）的權重改成 `weight`。有 `forS` 時，權重在 `forS` 秒內直線變過去（每 0.5 秒更新一次），之後維持；沒有 `forS` 或 0 時立刻改。從開始那一刻的權重算起，所以前一個移轉可以接著下一個。照權重分流的元件（使用者、DNS、CDN、API Gateway、負載平衡器、限流器、保險絲）馬上照新的權重送；API 伺服器、worker、快取會呼叫全部下游，不照權重（設計檢查會提醒）。這就是金絲雀發布、藍綠切換、整區撤出。DNS 不另外模擬 TTL：權重改了，下一個請求就照新的權重（DNS failover 的 TTL 照舊）。
- 網路分區（`partition`）：從 `atS` 起，`regions` 這兩區之間斷線（有 `forS` 時到 `atS + forS` 為止；可以重疊）。兩區之間的呼叫送不到：呼叫端等到自己的逾時（線的 `timeoutMs`，或使用者的逾時）。分區開始前送到、分區期間才做完的呼叫，回覆也送不回去。資料庫兩區之間的複製也送不到（副本記為沒收到）。使用者不在任何區域，兩邊都連得到。沒有區域的元件不會被切開。簡化：worker 從佇列拿訊息不受分區影響。資料庫的 split brain 見「資料庫的一致性」。
- 部署新版本（`rollout`）：從 `atS` 起分 `waves` 波（預設 1）把新版本（程式或設定）換到 `node` 的實例上。沒有 `node` 時是全域推送：所有 API Gateway、API 伺服器和 worker 一起換。第 w 波把每個目標的前 ceil(w ÷ waves × 台數) 台換成新版本（還沒開的自動擴充實例也算：開機後就是新版本），每波觀察 `waveS` 秒（預設 60）。新版本處理時間乘上 `slow`、多一個錯誤率 `errorRate`（和節點自己的錯誤率疊加：1 − (1 − a)(1 − b)；API Gateway 沒有自己的錯誤率，新版本的錯誤率照樣作用），`crash: true` 時換上就故障。有 `haltAt` 時，每波觀察完看新版本實例這一波的失敗比例（包含下游回來的失敗；少於 20 個請求算 0；crash 一律算 100%）：超過 `haltAt` 就把全部新版本回滾（當掉的實例恢復），停止部署。沒有 `haltAt` 時跑完全部波數，新版本一直留著。時間軸記錄每一波、回滾和完成。縮放執行時，部署的目標保留全部實例（每波的比例才準）。範例 `bad-config-push`。
- 重新分片（`reshard`）：從 `atS` 起把分片資料庫 `node` 改成 `toShards` 份。先複製資料 `forS` 秒（預設 60）：這段時間每一份（舊的和新的）處理時間乘上 1 + `copyLoad`（預設 0.5）。複製完切換：之後 key 照新的份數分（key 除以份數的餘數，所以大部分 key 換了分片）。新分片的實例從一開始就在（切換前閒著），所以使用率會被它們拉低。切換時不模擬短暫停寫，也不搬複製狀態（副本延遲、寫後讀從新分片重新算）。只能用在分片資料庫（設計檢查會擋）。
- 寫後讀（`traffic.followReads`）：每筆成功的寫入，有這個比例的使用者在 `followAfterMs`（預設 100）毫秒後讀同一個 key（另一條亂數串流，所以 0 時結果完全不變）。有 API 時，這個讀取呼叫使用者 API 組合裡第一個讀取 API；沒有讀取 API 就不送。這些讀取算在流量裡（offered）。
- 到達率上限是每秒 100 萬個請求（倍數疊太多時會被截在這裡）。
- 每個請求有：讀或寫（依 `readRatio`）、一個 key（依 Zipf 分佈，`zipf: 0` 是均勻）。
- 隨機數分成好幾條獨立的串流（到達、讀寫、key、抽樣、每個節點、每條邊）。所以兩個不同的設計跑同一個情境時，看到的流量完全一樣（common random numbers），比較才公平。

## 3. 元件的共同模型：站（station）

API 伺服器、API Gateway、worker、快取、資料庫、物件儲存都是「站」：

- 每個站有 `instances` 台實例。每台有 `concurrency` 個槽（slot，可以想成執行緒或連線）。
- 請求來了，有空槽就開始；沒有就排隊（FIFO）。排隊超過 `queueLimit` 就拒絕（`queue_full`）。
- **阻塞模型（blocking）**：請求在等自己的下游回應時，也一直佔著槽。這和真實的執行緒池一樣：下游變慢，上游的槽會被佔滿，整條路跟著變慢（連鎖變慢）。
- 處理時間服從 Gamma 分佈，用平均值（mean）和變異係數（cv）描述：`cv: 1` 是指數分佈，`cv: 0` 是固定時間。

## 4. 各元件

| 元件 | 行為 |
|---|---|
| 使用者（client） | 產生請求。請求超過 `clientTimeoutMs` 就算逾時。 |
| DNS | 解析快取沒命中時多花 `lookupMs`，然後轉給下一個節點。 |
| CDN | 讀取依 `hitRatio` 在邊緣直接回應；沒命中和寫入轉給來源。 |
| API Gateway | 站。做完自己的處理後轉給下一個節點。 |
| 負載平衡器 | 把請求分給下游所有實例：`round_robin`、`least_conn`、`p2c`（隨機挑兩台選比較閒的）、`random`。跳過它認為不健康的實例（見下面的「Health check 與 gray failure」）。 |
| 限流器 | `limit: rate`：token bucket，每秒補 `ratePerSec` 個 token，最多存 `burst` 個。`concurrency`：已放行、還沒回應的請求最多 `maxConcurrent` 個。`both`：兩個都檢查。超過就回 429（`rate_limited`）。`scope: per_client` 時每個使用者節點（租戶）各有一份額度；`appliesTo: batch` 時只限可丟棄的請求。 |
| API 伺服器（service） | 站。自己處理完，依序（或並行）呼叫下游。讀取時，如果同時接了快取和資料庫，就用 cache-aside：先查快取，沒命中才查資料庫，再非同步把值寫回快取。寫入時先寫資料庫，再讓快取失效。 |
| 保險絲（circuit breaker） | 看最近 `windowS` 秒的呼叫。失敗比例超過 `failureRatio`（且至少 `minCalls` 次）就跳開：`openMs` 內直接拒絕（`circuit_open`）。之後放 `halfOpenCalls` 個試探請求：全成功就關上，有一個失敗就再跳開。 |
| 快取 | 站。`fixed` 模式依 `hitRatio` 決定命中；`lru` 模式真的記住 key（容量 `capacityKeys`、可設 `ttlS`）。多台實例時用 key 分配。快取後面直接接資料庫時是 read-through／write-through。LRU 模式另有防擊穿設定，見下面「快取擊穿」。 |
| 資料庫 | 站。寫入到主庫；讀取依 `readFrom` 到副本或主庫。每筆寫入，每個副本也要花 `writeMs × replicaApplyRatio` 套用。 |
| 分片資料庫 | 用 key 分到 `shards` 個分片，每個分片是一個主庫（加副本）。熱門 key 會讓某個分片特別忙。 |
| 佇列 | 寫入花 `enqueueMs` 後馬上回應（ack）。訊息等 worker 有空槽時再交出去（competing consumers）。超過 `maxDepth` 拒絕。交付方式見下面「佇列的交付方式」。 |
| Worker | 站。從佇列拿訊息處理，再呼叫下游。從「進佇列」到「處理完」的時間算在非同步延遲。`poisonRate` 比例的訊息是毒訊息：每次處理都失敗（依訊息 id 固定）。 |
| 物件儲存 | 站。GET 花 `getMs`，PUT 花 `putMs`。 |

### 佇列的交付方式

- `delivery: at_most_once`（預設）：訊息交給 worker 就刪掉。worker 處理失敗或故障，訊息就遺失（算非同步失敗）。
- `delivery: at_least_once`（像 SQS）：訊息交給 worker 後隱藏 `visibilityTimeoutMs`，worker 成功才刪除。
  - 失敗或故障：時間到後訊息重新出現，排到佇列最後（記在 `redelivered`）。
  - 太慢：時間到時還沒做完，訊息也會重新出現；如果有空的 worker 拿走它，同一則訊息會做兩次（記在 `duplicates`）。所以 worker 要冪等。
  - `maxReceives` > 0：一則訊息被拿了這麼多次還沒成功，就移到 DLQ（記在 `dlq`，算非同步失敗），不再重試。0 = 沒有 DLQ，一直重試。
  - 已經被做完的訊息，如果還在佇列裡，輪到它時直接跳過。
- `messageTtlS` > 0：訊息從第一次進佇列算起超過這個時間，輪到它（或它重新出現）時就丟掉（記在佇列的 `expired`，算非同步失敗）。
- 設計檢查會提醒：visibility timeout 比 worker 的平均處理時間短；worker 有毒訊息但沒有 DLQ。
- `ordering: fifo`（像 SQS FIFO、Kafka 的 partition）：訊息依 key 分成 `groups` 組（key 除以組數的餘數，預設 16）。同一組一次只交出一則：前一則成功、最多一次時失敗、進 DLQ 或過期，才交下一則。其他的停在後面，第一次停下時記一次 `holBlocked`。所以組數也是同時能處理的訊息數上限。
  - 至少一次時，失敗的訊息要等 visibility timeout 後重新出現、再做；這段時間整組都在等。毒訊息會卡住整組，直到它進 DLQ（`maxReceives` 次 × visibility timeout）。這就是 head-of-line blocking。
  - 佇列深度算交得出的訊息加停在後面的訊息。

### 寫入同時送訊息：dual write 和 outbox

API 伺服器或 worker 的寫入計畫裡同時有一個儲存（資料庫、分片資料庫、object storage）和一個佇列時：

- `outbox: off`（預設）：兩個是分開的呼叫（照 `calls` 依序或平行）。一個成功、另一個失敗時（例如佇列故障、逾時），資料和訊息不一致，記在節點的 `dualWriteGaps`。依序時先寫儲存，所以常見的是「資料存了、訊息沒送」，使用者還看到失敗。
- `outbox: on`（transactional outbox）：訊息和資料在同一筆交易寫進儲存，所以請求不呼叫佇列，儲存寫成功就算成功。之後 relay 把訊息送到佇列；失敗就等 `outboxRetryMs`（預設 1000）再送，直到成功（記在 `outboxRetries`）。簡化：relay 不佔槽、不額外讀儲存（像 CDC 讀 log），訊息在 commit 後立刻送第一次。
- 只看儲存和佇列兩種步驟；快取失效、其他服務的呼叫照舊。

### 請求優先級和降載（load shedding）

- 每個使用者節點有 `priority`：`critical`（關鍵）、`normal`（一般，預設）、`batch`（可丟棄：batch、爬蟲、bot）。它送出的請求都帶這個優先級，非同步訊息也一樣。
- API Server 和 API Gateway 可以改排隊方式（Facebook〈Fail at Scale〉的做法）：
  - `queueOrder`：`fifo`（預設，先來先做）、`lifo`（後來先做）、`adaptive_lifo`（平常 FIFO；佇列最近 100 ms 都沒清空過時，改成 LIFO）。過載時 FIFO 輪到的請求，呼叫端多半已經逾時放棄；LIFO 先做最新的請求，做完的才有人收。代價是排在最舊的請求等更久，可能一直輪不到。
  - `codelTargetMs`（CoDel，0 = 關）：佇列最近 100 ms 內清空過時，一個請求最多排 100 ms；一直沒清空（塞車）時，最多排 `codelTargetMs`。輪到時已經排超過的請求，直接丟掉（`codel`），不做呼叫端可能已經不等的白工。`codel` 失敗會照 `retries` 重試。Facebook 用 5 ms 和 100 ms。
- API Server 和 API Gateway 有 `shedAt`（0 = 關）：一台的位置都滿、而且排隊數 ≥ `queueLimit × shedAt` 時，新來的 batch 請求直接拒絕（`shed`）。一般和關鍵請求照常排隊，直到排隊上限。
- 被降載和被限流（429）一樣，不重試。
- 這是簡化：排隊仍然是先到先做，沒有依優先級插隊；一般和關鍵請求沒有分開的門檻。
- 多個使用者節點可以當成不同的租戶或請求類別：結果裡每個使用者節點有自己的成功和失敗數，CLI 會列出各自的失敗率。
- 設計檢查會提醒：設了降載門檻或「只限可丟棄的請求」，但沒有使用者送 batch 請求。

### 資料庫副本的複製延遲（replication lag）

- 主庫寫完一筆，每個副本在 `replicaDelayMs` 後收到它，再排隊、花 `writeMs × replicaApplyRatio` 套用。
- 從主庫寫完到副本套用完，這筆寫入在副本上是「還沒套用」。副本的複製延遲 = 最舊一筆還沒套用的寫入，已經等了多久。
- 讀副本時，如果這個 key 有還沒套用的寫入，就算一次「讀到舊資料」（`staleReads`）。讀副本的總數記在 `replicaReads`。key 越集中（`keys.zipf` 大）、延遲越長，舊資料越多。
- `maxLagMs` > 0：選副本讀取時，跳過延遲超過這個值的副本（像 ProxySQL 的 `max_replication_lag`）。全部副本都太落後時，讀主庫，所以主庫會變忙。
- 每秒結束時，記下最落後的副本延遲（`replLagMs`），整次執行的最大值是 `maxReplLagMs`。
- 副本故障、佇列滿時，送不到的寫入記在 `replicationDropped`，不再算「還沒套用」。這是簡化：真的資料庫會在副本恢復後補上，期間那個副本一直落後。
- `replicaApplyRatio` = 0 時不模擬複製，也不計算舊資料。
- 寫後讀（情境的 `followReads`）：讀副本時，如果這個 key 在副本上有「commit 時間不晚於這個使用者那筆寫入」的還沒套用寫入，這個使用者就看不到自己的寫入，算一次 `rywMisses`。
- `readYourWrites: primary`：寫後讀在寫入後 `rywWindowMs`（預設 2000）毫秒內送到主庫（像「寫完一段時間讀主庫」的 session 規則）。`rywMisses` 變 0，主庫讀取變多。視窗比複製延遲短就沒用。

### 資料庫的一致性：列鎖和 split brain

- 列鎖（`locks: row`）：寫入同一個 key 要先拿這個 key 的鎖。鎖被別的寫入拿著時，這筆寫入等著（佔著連線槽），算一次 `lockWaits`。寫完後交易再握鎖 `lockHoldMs` 毫秒才 commit、回覆、放鎖（交易裡還有別的查詢）。所以一個 key 每秒最多 1000 ÷（`writeMs` + `lockHoldMs`）筆寫入。熱門 key（`zipf` 大）會讓寫入排成一列。故障時，鎖跟著交易一起消失。扇出寫入（每個副本都寫）不拿鎖。讀取不拿鎖（像 MVCC）。開了列鎖時不縮小模擬（k = 1）：縮小流量會讓熱門 key 的寫入變少，看不出競爭。
- 網路分區和自動 failover：分區開始時，主庫和某個副本在被切開的兩邊，而且開了 `failover: auto`，就在 `failoverS` 後檢查：還切開、主庫沒故障，就把對面最跟得上的副本升為主庫（遺失它還沒收到的寫入，記在 `lostWrites`）。簡化：failover 控制器在副本那一側，所以它看不到主庫就以為主庫故障。
- 舊主庫還活著（zombie）。它那一側連不到新主庫，寫入就送到舊主庫，commit 成功，但不複製給任何人。這些寫入記在 `divergentWrites`：分區結束時，時間軸寫出「舊主庫在分區期間收了幾筆寫入，新主庫沒有」。舊主庫之後變成新主庫的副本。不模擬合併或回滾那些寫入。
- `fencing: on`：新主庫一升起，舊主庫就拒絕寫入（`down`），連正在做的寫入也不能 commit（像 epoch token）；分區結束、舊主庫變回副本時還沒做完的寫入也一樣。沒開 fencing 時，這些寫入算分歧。不再分歧，代價是舊主庫那一側在分區期間不能寫。
- 範例 `split-brain`。

### 自動擴充（autoscale）

API Gateway、API 伺服器和 worker 可以開 `autoscale: on`，行為像 Kubernetes HPA：

- `instances` 是最少台數，`maxInstances` 是最多台數。
- 每 `scaleEveryS` 秒看一次上線實例的忙碌程度（佔用的槽 ÷ 全部的槽）。差距在 10% 以內不動；否則想要的台數 = `ceil(上線台數 × 忙碌程度 ÷ targetUtil)`，限制在最少和最多之間。
- 擴充：新實例先開機 `bootS` 秒（不接請求），上線後 `warmS` 秒內是冷的：處理時間乘上 `coldFactor`，隨時間線性降回 1 倍。
- 縮減：只在沒有實例開機時。想要的台數要在 `scaleDownS` 秒（縮減穩定窗，預設 300）內每次檢查都比上線台數少才減；一次減到這段時間內想要的最多台數。被減的實例不再接新請求，手上的工作做完才關。
- 自動擴充的節點，使用率用「開著的時間」當分母；沒有排隊理論對照值。
- 結果的 `autoscale` 有最少、最多、最高同時上線、結束時上線、開機次數和關機次數。時間軸記錄每次擴充、上線和縮減。
- 開機依賴：從自動擴充節點出發、`on: boot` 的線只在開機時用。每台新實例開機 `bootS` 秒後，對每條 boot 線呼叫一次（一個讀取，照線的逾時和重試）；全部成功才上線，有一個失敗就記一次 `bootFails`，再等 `bootS` 秒重開。重開期間它還算「開機中」，所以不會多開別台。一般請求不走 boot 線；boot 線不算迴圈。像拿設定、向服務註冊、拉映像檔：那個下游壞了，就加不了機器。範例 `provisioning`。
- 控制面依賴：`on: control` 的線給節點的控制器用：自動擴充每次檢查前、資料庫自動 failover 決定前（故障和網路分區兩種）、DNS failover 每秒的健康檢查前，對每條 control 線呼叫一次（一個讀取，照線的逾時）。全部成功才照常做；有一個失敗，這次就不動作（看不到監控），記一次 `blindChecks`，時間軸記錄看不到和恢復。failover 看不到時，每 `failoverS` 再試一次，直到主庫恢復、已經換掉或分區結束。像監控系統跑在它要監控的叢集上、服務發現跟著故障（Roblox 2021、AWS us-east-1 2021）。一般請求不走 control 線；control 線不算迴圈。設計檢查會提醒：control 線的起點沒有控制器；boot 或 control 線沒有設逾時（被分區切開時會一直等）。範例 `blind-autoscaler`。

### 函式（function，像 AWS Lambda）

`function` 是無伺服器函式。它不用自動擴充，而是每個請求各用一個執行環境：

- 每個執行環境一次只處理 1 個請求，不排隊。等下游時也占著這個環境。
- 請求到達時，先用最近閒下來的環境（溫的）。沒有空的，就開一個新的：冷啟動 `coldStartMs`，這段時間算在這個請求的延遲裡。
- 同時的環境數（開著的，含冷啟動中的）不超過 `maxConcurrency`。開新環境的速度不超過每 10 秒 `scalePer10s` 個（token bucket，一開始是滿的）。兩個條件有一個不允許，同步的請求就被拒（`rate_limited`，429）。
- 閒置 `idleS` 秒的環境被收回（每 min(`idleS`, 10) 秒檢查一次）。`provisioned` 個環境一開始就備好、不收回，也算在上限裡。
- 環境用到才建立；收回的環境之後重用。所以實例數最多是「同時開著最多的那一刻」，不是 `maxConcurrency`。
- 從 queue 來（event source mapping）：每則訊息先找溫的環境；沒有，就開新環境（每則訊息最多開一個）。到了上限或擴充速率，訊息留在 queue 裡等，不算失敗。環境做完一則就再拿下一則。簡化：沒有模擬 SQS 輪詢器自己的擴充速度（AWS 是每分鐘最多加 300 個併發）。
- 負載平衡器和 API Gateway 把請求交給函式本身，由函式挑環境。
- 使用率 = 忙碌的環境數 ÷ `maxConcurrency`（瓶頸也這樣比）。結果的 `function` 有上限、`provisioned`、最多同時開著的環境、結束時開著的環境、冷啟動次數和被拒次數。沒有每個環境一列，也沒有排隊理論對照值。
- 縮放執行時，`maxConcurrency`、`provisioned`、`scalePer10s` 都除以 k；k 最多到 `maxConcurrency` ÷ 10（至少留 10 個環境）。
- 沒有做：部署新版本（`rollout`）不換函式的環境；指定某一個環境的故障事件。範例 `serverless-db`。

### 快取擊穿（cache stampede）

熱門 key 過期後，在第一個請求把值寫回之前，所有讀這個 key 的請求都沒命中，一起去查資料庫。查詢越慢、key 越熱，同時去查的請求越多。這三個設定只在 `lru` 模式有作用：

- `ttlJitter`：每次寫入時，TTL 乘上 (1 − `ttlJitter` × u)，u 是 0 到 1 的亂數。同一時間寫入的 key（例如冷啟動時）就不會同一時間過期。
- `stampede: coalesce`（合併查詢，singleflight）：快取後面直接接資料庫（read-through）時，同一台快取上同一個 key 同時只查一次；其他沒命中的請求不佔槽，等那一次的結果。結果算 `coalesced`。快取故障時，等待的請求一起失敗。
- `stampede: lease`（Facebook memcache 的做法）：服務自己查資料庫（cache-aside）時，第一個沒命中的請求拿到這個 key 的 lease，去查資料庫再寫回。lease 有效期間（`leaseMs`），其他沒命中的請求收到「等一下」，`leaseWaitMs` 後再問一次快取。寫回或刪除這個 key 時 lease 結束。一個請求最多等 `leaseMs`，之後自己去查資料庫（不拿 lease）；請求的 deadline 過了也不再等。等待次數算 `leaseWaits`；每次「等一下」也算一次沒命中（命中率的分母包含它）。
- 沒有模型化：lease 防止「舊值覆蓋新值」（stale set）的效果。這個模擬器不追蹤快取裡的值新不新。

### 快取跨區複製

- 快取 → 快取的線是跨區複製，不是呼叫：來源快取每次寫入（cache-aside 的寫回、read-through 的填入、write-through）和刪除，經過這條線的延遲（兩區不同時是跨區延遲）之後，套到目標快取上負責這個 key 的那台，用目標的 TTL。不佔目標的槽。複製過去的不再往外複製，所以兩邊互連不會來回繞（設計檢查不把它當迴圈）。
- 目標那台故障時，這筆複製丟掉。送出或送到時兩區之間網路分區，也丟掉（分區結束前送出的，結束後才到也丟）。結果裡目標快取的 `replicationApplied`、`replicationDropped` 是套用和丟掉的筆數。
- 只有 LRU 模式的快取有作用（固定命中率模式沒有 key）。
- 用途：整區撤出時，接手那一區的快取已經是熱的（範例 `region-cutover`）。

## 5. 邊（呼叫）

- `latencyMs`：單程網路延遲，去和回各算一次。從使用者出發的邊預設 20 ms，其他預設 0.5 ms。
- `on`：`all`、`read`、`write`、`boot` 或 `control`，決定哪些請求走這條邊（`boot`：只有自動擴充的新實例開機時呼叫；`control`：只有節點的控制器呼叫，見「自動擴充」）。
- 建立連線（`connectMs`，0 = 不算）：每一份呼叫要一條連線。呼叫端的每台實例對每條邊有一個閒置連線池：送出時拿最新的閒置連線；沒有，或最新的也閒置超過 `idleS` 秒（預設 60，那就全部關掉），就開一條新的，先付 `connectMs`（TCP＋TLS 握手），記在邊的 `connects`。呼叫結束時連線放回池（逾時的呼叫連線重設，不放回）。`keepAlive: off` 時每份呼叫都開新連線。所以同時呼叫的數量變多（流量突增、下游變慢）時，要開更多連線，延遲跟著變高。不模擬連線數上限、TLS session 恢復或伺服器端的握手成本。
- `weight`：一個節點有多條同類邊時，依權重分配。權重 0 的邊不收流量。
  - 負載平衡器：各邊權重都一樣時，所有邊後面的實例合成一個池，照策略挑（和沒有權重一樣）。權重不一樣時，先依權重挑一條邊（跳過後面沒有健康實例的邊；都不健康時在全部裡挑），再在那條邊的實例裡照策略挑。重試只在同一條邊的實例裡換。
- `timeoutMs`：呼叫者等多久就放棄。**被呼叫的一方不知道呼叫者放棄了，會繼續做完**（白做的工）。
- 截止時間傳遞（deadline propagation）預設關閉：使用者放棄以後，中間的服務照樣呼叫下游、照樣重試。真實系統沒做這件事時就是這樣，也是重試放大流量的原因之一。使用者元件設 `deadline: propagate` 時，請求帶著截止時間 = 送出時間 + `clientTimeoutMs`：
  - 每一跳最多等 `min(timeoutMs, 剩下的時間)`。
  - 過了截止時間就不送出、不重試。
  - 排隊排到過了截止時間的工作，開始前直接丟掉，記在節點的 `expired`，不算該節點的失敗。
  - 佇列訊息是新的請求，不帶截止時間。
- 負載平衡器的連線數（`least_conn`、`p2c` 用的）從送出開始算，到回覆送回來或呼叫者逾時放棄為止。回覆在呼叫者放棄之後才回來，算「太晚」（`late`）。
- Health check 與 gray failure：gray failure 是「實例還活著，但變慢或一直出錯」。情境的 `slow` 和 `errors` 加上 `instance` 時，只影響那一台。負載平衡器的 `healthCheck` 決定它怎麼知道哪台壞了：
  - `instant`（預設，理想化）：立刻知道哪台故障（`down`），但不知道變慢或出錯。
  - `liveness`：每 `hcIntervalS` 秒檢查每台一次（各台的檢查時間平均錯開）。只有故障的實例檢查失敗。連續 `hcThreshold` 次失敗才移出，移出後連續 `hcThreshold` 次成功才放回。所以故障後約 `hcIntervalS` × `hcThreshold` 秒內，請求還是會送到故障的實例（失敗原因 `down`）。
  - `deep`：像真的請求一樣檢查。以那台的錯誤率失敗；預估時間（服務時間 × 變慢倍數 ×（1 + 排隊數 ÷ 槽數））超過 `hcTimeoutMs` 也算失敗。這是簡化：檢查本身不佔槽，也不算進統計。
  - 檢查把所有實例都移出時，負載平衡器改送給所有已註冊的實例（fail open，和 AWS ALB、Envoy 的 panic threshold 一樣）。
  - `outlier: on`（被動檢查，像 Envoy 的 outlier detection）：看真實請求的回覆。同一台連續 `outlierErrors` 次失敗就剔除 `ejectS` 秒，之後放回來再試。算失敗的是像 Envoy consecutive 5xx 的回覆：錯誤、逾時、故障，和過載的拒絕（排隊滿了、降載、CoDel）。依賴的元件造成的失敗也算（真實的 proxy 也分不出來），所以最多同時剔除一條邊後面現在服務中實例的一半（至少 1 台；自動擴展還沒開的實例不算）。成功和其他回覆（例如限流的 429）把連續失敗數歸零。負載平衡器後面是資料庫、快取或不分實例的元件時，health check 和自動剔除不作用：那個目標被當成一個整體，故障時立刻跳過（設計檢查會提醒）。
  - 結果：負載平衡器的 `hcRemoved`（health check 移出次數）和 `ejections`（剔除次數）。
- 佇列交給 worker 的線不看 `timeoutMs`、`retries` 和 `throttleK`；設計檢查會提醒。失敗後要不要重送，由佇列的 `delivery` 決定。
- `retries`、`backoffMs`：失敗後重試，等待時間是 full jitter：`random(0, backoffMs × 2^(n−1))`。被限流（429）、被降載（`shed`）、保險絲跳開和呼叫端自我限流（`throttled`）都不重試。
- `retryBudget`（重試預算，0 = 不限）：最近 10 秒內，這條邊的重試數最多是第一次呼叫數的 `retryBudget` 倍（例如 0.1 = 10%）。超過時不重試，直接回傳失敗，記在邊的 `denied`。重試在送出時才算。這是 gRPC retry throttling、Envoy retry budget 的簡化版。
- `throttleK`（呼叫端自適應限流，0 = 不用）：Google SRE 書「Handling Overload」的 client-side adaptive throttling。呼叫端記住最近 10 秒這條邊的 requests（送出的呼叫，加上在本地擋掉的）和 accepts（成功的呼叫）。每次要送出前，以機率 max(0, (requests − K × accepts) ÷ (requests + 1)) 在本地直接失敗（`throttled`），不送出去，也不重試。
  - 送出的呼叫在結果知道時（回覆、逾時）才算進 requests，所以還在路上的呼叫不會被當成失敗。送出 5 秒還沒有結果的呼叫，在第 5 秒先算進 requests（沒有 accept）；之後成功只再加一個 accept。所以下游完全卡住、又沒設逾時時，自我限流也會啟動。在本地擋掉的呼叫立刻算進 requests。
  - 穩定過載時，送出的呼叫約是成功數的 K 倍，其他在本地擋掉；下游少做很多白工。代價：有些擋掉的呼叫其實下游有空，所以成功數會少一點。
  - 書上用 2 分鐘的窗口；這裡的模擬時間短，用 10 秒。
  - 恢復要時間：下游全部失敗一陣子後，窗口裡幾乎都是失敗，呼叫端只放很少的呼叫出去。每次成功多放大約 K 次，送出量慢慢變大；要等成功數追上 requests ÷ K 才完全不擋。

## 6. 指標

- `bulkhead`（隔艙，0 = 不限）：呼叫端每台實例最多同時有幾個呼叫走這條邊（Hystrix 的 thread-pool bulkhead）。名額從送出開始佔用，到回覆或逾時為止；重試等待時不佔。滿了就在本地直接失敗（`bulkhead`），不送出、不重試。呼叫端是 API Server、API Gateway、Worker、快取時，名額是每台實例各自的；呼叫端不分實例時（例如負載平衡器、保險絲），名額是整條邊共用。
- `fallback: on`（降級回應）：這條邊的呼叫最後還是失敗（重試用完、逾時、保險絲跳開、隔艙已滿、自我限流）時，呼叫端改用備用回應：呼叫算成功，但標成「降級」，一路往上傳。使用者收到的成功回應裡，有降級的另外算在 `summary.degraded`（只有設計裡有邊開了 fallback 時才有這個欄位）。邊的 `fallbacks` 是改用備用回應的次數。快取旁路（cache-aside）讀資料庫時拿到降級回應，不會寫進快取；read-through、write-through 也一樣。快取旁路（cache-aside）的查詢不用降級回應：呼叫端也連著資料庫，快取查不到或故障時本來就會去讀資料庫（設計檢查會提醒）。read-through 快取不同：呼叫端只連快取，快取故障時降級回應照樣作用。保險絲（circuit breaker）出去的邊開了降級回應時，保險絲還是把那次呼叫算成失敗，所以下游壞掉時照樣會跳開；跳開後被擋下的呼叫也改用降級回應，不會回 `circuit_open`。
  - 只開 fallback 不夠：呼叫還是要等到逾時才失敗，呼叫端的槽一樣被卡住。只開 bulkhead 也不夠：擋下的呼叫讓請求失敗。兩個一起用，慢的下游只卡住幾個名額，其他請求立刻拿到降級回應。
- `hedgeMs`（對沖請求，0 = 不用）：讀取送出 `hedgeMs` 還沒有回覆，就再送一份（Dean & Barroso〈The Tail at Scale〉的 hedged request）。只對讀取；寫入重送不安全，不對沖。
  - 經過負載平衡器時，第二份送到另一台實例（只有一台時才可能同一台）。第二份也佔隔艙名額；名額滿了就不送第二份。逾時（`timeoutMs`）算整次呼叫，不是每份各算。
  - 先成功的那份算數。一份失敗、另一份還在路上時，等另一份；兩份都失敗才算失敗（然後照 `retries` 重試，重試也會對沖）。
  - 輸的那份下游照樣做完（不取消），回來時不算「放棄後才回來」（`late`）。第二份算在邊的 `calls` 裡，另外記在 `hedges`；第二份先成功的次數記在 `hedgeWins`。
  - 通常把 `hedgeMs` 設成這條邊平常的 p95：多送約 5% 的呼叫，就能把一台慢實例造成的長尾壓下來。
- `fanout`（扇出，0 或 1 = 只送一份）：每個呼叫同時送給終點的 `fanout` 份（scatter-gather），每份是一個獨立的工作，佔終點的槽、各自排隊。
  - 分片資料庫：送給 key 所在的分片和接下來的分片，最多全部分片。每個分片照平常的規則選主庫或副本。一個分片沒有能服務的實例時，那份直接失敗（`down`）。
  - 資料庫：送給主庫和副本裡的 `fanout` 台（寫入一定包含主庫）。寫入直接寫到每一份（像 Cassandra 的 leaderless 寫入），不再另外複製，所以不計算副本延遲和讀到舊資料。
  - 其他有實例的節點（API Server、Worker、快取、物件儲存）：送給不同的、正在服務的實例，輪流挑起點。自動擴充中還在開機或正在退役的實例不收；故障的實例算一份失敗。終點沒有實例（負載平衡器、佇列、保險絲…）時不作用（設計檢查會提醒）。
  - 從佇列或負載平衡器出發的線不作用：佇列把每個訊息交給一個 worker，負載平衡器每次只挑一台（設計檢查會提醒）。要送給多台，請在呼叫端直接連到終點的那條線上設扇出。
  - 大於可用的數量時，就送給全部。扇出時不送對沖請求。逾時、重試、隔艙都算整次呼叫。邊的 `copies` 是送出的份數；終點的 `arrivals` 每份各算一次。
  - 長尾放大：一份慢的機率是 p 時，N 份裡至少一份慢的機率是 1 − (1 − p)^N。100 份、每份 1% 慢，63% 的呼叫會碰到慢的那份（〈The Tail at Scale〉）。
- `quorum`（0 = 等全部送出的份數）：扇出時，成功的份數到 `quorum` 就回覆；失敗的份數多到湊不到 `quorum` 時就失敗（用第一個讓它湊不到的失敗原因）。`quorum` 比 `fanout` 大時當作 `fanout`。能送的份數比 `quorum` 少時（例如只有 1 台、扇出 3、等 2），呼叫一開始就失敗（`down`，像 Cassandra 的 UnavailableException），不會把 `quorum` 降到能送的份數。沒等到的份數照樣做完，下游負載不變。3 份等 2 份時，一份慢或一份故障都看不出來；等全部時，最慢的那份決定延遲。
  - 情境的 `scale`（模擬 1/k 的流量和容量）不會減少扇出終點的實例數：份數和真實一樣。
- 暖機（`warmupS`）期間的資料不算進總結。
- 使用率、吞吐量、每個元件的 rps：只算「暖機後到流量結束」這段。
- 量測區間是「暖機後的第一個完整窗口」到「流量結束前的最後一個完整窗口」。時長不是窗口的整數倍時，最後不滿一個窗口的部分不算。窗口太長、放不下一個完整窗口時，會自動縮短並提醒。
- 總結（送出、成功、失敗、延遲）：所有在量測區間內**送出**的請求，一直追到它結束（包括流量結束後才完成的）。
- 每個時間點（每秒）的成功數、失敗數和延遲，按**完成**的時間算；送出數按送出的時間算。這和監控儀表板一樣：塞車時，這一秒完成的多半是前幾秒送出的請求。
- 模擬在「流量結束＋使用者逾時」時停止。這時還沒做完的背景工作（佇列裡的訊息、副本套用、使用者放棄後的重試）不會做完，數量記在結果的 `unfinished`：實例上正在跑或排隊的工作、快取等資料庫回覆時保留的工作、線上還在傳的呼叫和回覆、還沒送出的重試、佇列訊息。等下游回覆的工作在每個實例上各算一次。
- 每 `windowS` 秒輸出一個時間點：每個節點的使用率、排隊長度、命中率、保險絲狀態；每條邊的呼叫數。
- 延遲百分位數用對數分桶的直方圖，誤差小於 0.5%。

## 6.1 成本和複雜度（學習用，不影響模擬）

- 成本（`src/learn/cost.ts`）是示意價格，接近 2026 年 AWS 的比例，不是報價。照一次執行的平均流量算一整個月（730 小時）。
  - 機器（API Server、Worker、快取、資料庫、分片資料庫）：每台每小時 = 單價 × (0.5 + 0.5 × 同時處理數 ÷ 預設值)。一半是機器本身，一半跟著大小走：加大同時處理數比加一台便宜，但不是免費。單價：API Server $0.08、Worker $0.08、快取 $0.15、資料庫 $0.25（每台主庫或副本；分片資料庫是分片數 ×（1 + 副本數）台）。
  - 自動擴充：用這次執行裡平均在服務的台數。
  - 託管元件：負載平衡器每小時 $0.025 ＋每百萬請求 $0.003；API Gateway 每百萬 $3.5；佇列每百萬 $0.4；CDN 每百萬 $1；DNS 每百萬 $0.4。
  - 物件儲存：每百萬寫入 $5、讀取 $0.4。送給使用者的流量：每個請求 2 KB，每 GB $0.09。跨區流量：引擎在每條線上數「真的跨兩區」的訊息：送到和呼叫端不同區的實例的每一份（含重試、扇出的每一份、送到別區副本的讀取、failover 後搬到別區的主庫），加上每筆跨區快取複製（同區的快取複製不算）；每筆算 2 KB，每 GB $0.02。資料庫跨區副本的複製流量不算。
- 複雜度點數（`src/learn/constraints.ts`）代表團隊要建和顧的東西：人少、期限短，上限就低。每個元件 0–5 點（分片資料庫 5、快取／資料庫／佇列 2、其他 1、使用者和 DNS 0）；讀副本、自動切換主庫、自動擴充、outlier detection、主動健康檢查、防擊穿、對沖請求、扇出、降級回應、隔艙、自我限流、重試預算各 1 點；多區域 5 點。
- 限制條件題目：失敗率、p99、每月成本、複雜度都是門檻；全部達到才過關，分數 = 50 + 50 × (預算 − 成本) ÷ 預算。

## 7. 和排隊理論對照

每個站會附一列理論值：用實際的到達率、平均佔用時間和它的變異，套 M/G/c 近似（Erlang C 加上 Allen–Cunneen 修正）。

- 單一 M/M/1、M/M/c、M/D/1 站，模擬結果和公式的差距在幾個百分點內（見 `tests/queueing.test.ts`）。
- 負載平衡器分配得比隨機平均，實際排隊會比理論少。
- 有請求因排隊滿被拒時，理論值（假設排隊無上限）只供參考。

## 8. 刻意沒做的事

- 沒有封包、頻寬；網路只是固定延遲（加上元件的分佈）。TCP 只算建立連線的時間（`connectMs`），不算壅塞控制。
- 沒有記憶體、CPU 核心數；GC 只用情境的 `pause` 事件表示；「槽」就是容量。
- 快取沒有記憶體大小，只算 key 數。
- 資料庫的鎖只有列鎖（同一個 key 的寫入排隊）：沒有死鎖、表鎖、讀鎖、交易重試或衝突中止。副本恢復後不補資料。split brain 只計數分歧的寫入，不合併。
- 故障是立刻發生、立刻恢復。上游多久才發現，要看設定：負載平衡器的主動健康檢查、outlier detection 和 DNS 的偵測時間都有延遲；沒開這些的節點，上游要靠逾時和錯誤才知道。自動擴充只看忙碌程度，不看排隊長度或延遲；開機依賴只在開機時呼叫一次，上線後不再檢查。部署新版本之後才由自動擴充開的實例，如果它的那一列還沒被換過，就是舊版本；`crash` 版本在還沒開的實例上，開機後不會當掉。快取故障後恢復時是空的（冷快取）；故障當下正在讀穿或寫穿的請求算失敗。
